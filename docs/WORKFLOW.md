# Project workflow

This document defines the default process for projects developed in MR Web Lab. Adapt it to the actual scope; not every project needs every stage.

## 1. Brief

Record:
- Business or project context.
- Target audience and geographic market.
- Primary user needs and business goals.
- Required pages and functionality.
- Content and assets available.
- Constraints, assumptions, and open questions.

Do not invent business claims, testimonials, property details, prices, or credentials.

## 2. Art direction

Define:
- Brand personality and positioning.
- Visual references and anti-references.
- Color palette and typography.
- Photography and illustration direction.
- Layout principles and visual hierarchy.

The visual identity should respond to the project, not to a generic lab-wide template.

## 3. UX/UI

Map the page structure and key user journeys. Prepare wireframes or section outlines before polishing visual details. Account for mobile layouts from the beginning.

## 4. Prototype

Build the smallest useful functional version. Prefer semantic HTML, CSS, and JavaScript. Add a framework only when it solves a real project need.

## 5. Review

Check:
- Responsive behavior at common viewport sizes.
- Navigation and interaction states.
- Readability, contrast, and keyboard basics.
- Content consistency and image quality.
- Loading behavior and obvious console errors.

## 6. Demo deployment

Publish static prototypes with GitHub Pages when appropriate. Keep deployment instructions in the project's own README. Never commit API keys, passwords, private customer information, or production credentials.

## 7. WordPress implementation

Translate the approved structure into WordPress. Identify content types, taxonomies, custom fields, templates, and plugin requirements before implementation. Validate the result against the prototype without assuming every front-end interaction maps directly to WordPress.
